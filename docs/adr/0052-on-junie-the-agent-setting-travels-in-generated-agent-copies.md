# On Junie the agent setting travels in generated agent copies

On Junie a role's agent setting has its own git config keys, `orchestrator.junie.model.<role>` and `orchestrator.junie.effort.<role>`, and reaches Junie in generated copies of the plugin's agents. `orch.sh agent sync` writes each copy into the checkout's `.junie/agents/` with `model:` and `reasoningLevel:` added to its frontmatter, each only when set, and a marker line saying sync owns it, keeps the copies out of git through `.git/info/exclude`, and only ever writes over or deletes a file carrying the marker. We chose this over mapping Claude Code's aliases to Junie model IDs, and over waiting for Junie to take a model when it starts a subagent. A probe on Junie CLI 3419.7 showed that Junie honours a project-scope agent file's `model` and `reasoningLevel`, that a project copy wins over the plugin's agent of the same name, that non-Claude models work, that its alias `opus` resolves to Opus 4.8 rather than the latest Opus, and that an unrecognised model falls back to the session's model with only a log warning. An alias table would go stale and could not name non-Claude models.

A copy can go stale after a plugin upgrade or a setting change, so on Junie every skill runs `agent sync` once per run, before its first plugin agent, and `orch.sh doctor` warns when the copies differ from what sync would write. A mistyped model falls back silently, so doctor reads Junie's log to report what each agent ran on, and fails on Junie's `Unrecognized 'model' value` for a model currently set. If Junie's capability filter hides a copy a skill names, the first tier of `docs/host-capabilities.md`'s **Start a fresh subagent** fallback, a general-purpose agent briefed with the agent's file, runs without the setting and is recorded as a host fallback.
